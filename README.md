# vibe-need-judge

> 判断一个 vibe coding 应用到底解决了真痛点、只是痒点、还是创作者自嗨。
> 通过多 agent 法庭辩论，不迎合人类，纯粹从理性客观角度判断。

## 这是什么

`vibe-need-judge` 是一个 prompt-based skill，用来回答一个问题：

> **"我 vibe coding 出来的这个应用，到底解决了一个真痛点，还是只是我的自嗨？"**

它不靠创作者自我感觉，也不靠单一 AI 一家之言。它把这个问题交给一个**多 agent 法庭**：

- **消费群体当陪审团**（独立子 agent，动态匹配，权重占 60%）—— 模拟真实用户的行为反应
- **5 位专家当证人**（主上下文扮演，权重共 40%）—— 产品经理 / 代码工程师 / 备案中介 / 竞品分析师 / 增长黑客
- **两轮聚焦辩论** —— 第1轮独立举证，第2轮分歧质询
- **加权裁决** —— 痛点 / 痒点 / 自嗨 三档结论 + 建设性意见

**核心原则：不迎合人类。** 每个 agent 默认中立举证，消费群体子 agent 输入隔离、互不可见，保证独立思考。

## 核心设计

| 维度 | 设计 |
|---|---|
| 输入 | 灵活输入（想法 / PRD / 成品 URL），skill 自动判别阶段 |
| 输出 | 默认"评分+关键论点+裁决"；用户要求时给完整辩论实录 |
| 机制 | 混合：消费群体走独立子 agent，5 位专家证人在主上下文扮演 |
| 硬约束 | 省 token，总预算 8000 |
| 知识库 | 分层：核心画像候选库 + 案例库按需读 |
| 姿态 | 中立举证 + 加权裁决 + 附建设性意见 |
| 权重 | 消费群体 60%（内部按相关度动态分），专家 40%（各 8%） |
| 辩论深度 | 两轮聚焦辩论，第2轮重派涉分歧子 agent |
| 消费群体 | 候选库 7 个，动态匹配 2-3 个 |
| 降级规则 | 专家补证跳过 → 案例库关闭 → 第2轮只处理 1 个分歧点 |

### 三档裁决

| 档位 | 定义 | 触发条件 |
|---|---|---|
| **痛点** | 解决真实刚需，用户愿意付费/持续使用，市场可跑通 | 加权总分 ≥ 7.0 且消费群体 PAY_INTENT 均值 ≥ 6 |
| **痒点** | 有趣但不刚需，用户会用但不付费/不留存 | 加权总分 4.0–6.9，或 PAY_INTENT 均值 3–5 |
| **自嗨** | 创作者自我感动，目标群体根本不买账 | 加权总分 < 4.0，或消费群体 PAY_INTENT 均值 < 3 |

## 使用方法

### 安装

把 `vibe-need-judge/` 文件夹放到你的 skills 目录（具体路径取决于你的宿主 AI 环境）。

### 触发

对宿主 AI 说：

- "判断这个 vibe coding 应用/项目……"
- "这个应用是自嗨还是痛点"
- "这个项目解决需求了吗"
- "评价一下这个 vibe coding"
- "这个想法值不值得做"

### 输入

支持三种输入（skill 自动识别阶段）：

| 输入阶段 | 可信度 | 说明 |
|---|---|---|
| 想法点子 | 低 | 只有概念，技术/市场/合规都没验证 |
| PRD 说明 | 中 | 有结构化设计，但未经验证 |
| 成品 URL | 高 | 可观察实际产品，消费群体可"真实体验"后判断 |

### 输出

默认紧凑版裁决报告（11章节，≤1200 token）：

1. 一句话裁决
2. 输入阶段识别
3. 产品画像摘要
4. 评分总览
5. 消费群体陪审团（动态加权）
6. 关键论点（每方≤2条）
7. 分歧点（第2轮质询结果）
8. 置信度
9. 关键风险点
10. 建设性意见
11. 完整辩论实录（可选，用户要求时追加）

## 元自评：这个 skill 判断自己是什么？

> 诚实的元测试：用 `vibe-need-judge` 判断 `vibe-need-judge` 自己。

### 裁决：痒点

| 维度 | 得分 |
|---|---|
| 需求真伪度 | 4.9/10 |
| 付费/留存意愿 | 4.7/10 |
| 技术可行性 | 7.3/10 |
| 市场可跑通 | 5.1/10 |
| 合规风险 | 8.6/10 |
| **加权总分** | **6.1/10** |

### 一句话理由

需求真实但频次低、平替多（直接问AI/发社区），开源免费会用但不构成刚需，典型的"锦上添花"工具。

### 关键风险点

1. **用完即走无留存** — 一项目判1-3次，无持续使用场景
2. **最强平替是"直接让AI多角色评价"** — 输入隔离技术上成立但用户难感知差异
3. **创作者=用户典型场景** — 独立开发者做给独立开发者，存在自嗨风险

### 如何从痒点升级为痛点

- **转持续验证**：从"单次判断工具"升级为"项目持续验证看板"，跟踪想法→MVP→上线各阶段的判断变化
- **强化可感知差异**：在报告里明确标注"本判断由N个独立AI agent互不可见得出"，让用户感知与"直接问AI"的本质区别
- **加入历史对照**：用同赛道类似项目的实际结局做基准对比，用真实数据压住自嗨

### 元判断的诚实声明

这个裁决有个内在张力：**我在用这个 skill 判断这个 skill，而 skill 的核心原则是"不迎合人类"**。作为执行者，我没有迎合创作者——裁决是"痒点"而非"痛点"，并明确指出了"创作者=用户自嗨风险"这个最致命的问题。

但也要承认：**专家证人在主上下文扮演，不是真正独立AI**——这是 skill 自己的"已知局限"。所以这个"痒点"结论的置信度也只能是"中"。

---

## 已知局限

- **消费群体仍是被模拟的**：子 agent 按画像模拟，不等于真实用户调研，裁决是"理性推断"而非"市场验证"
- **专家证人在主上下文扮演**：不是真正独立 AI，可能有立场泄漏，但通过消费群体子 agent 独立性对冲
- **无真实数据支撑**：不抓竞品数据、不查真实留存，全靠 agent 推理，适合早期筛选不适合最终决策
- **中文产品语境**：备案中介角色针对国内合规，海外产品需调整
