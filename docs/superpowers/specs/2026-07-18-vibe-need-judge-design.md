# vibe-need-judge 设计文档

> **Skill 名称**：`vibe-need-judge`（vibe coding 需求真伪裁决）
> **创建日期**：2026-07-18
> **状态**：设计定稿，待用户审阅

---

## 0. 核心理念

把"这个 vibe coding 应用到底解决没解决真需求"这个问题，交给一个**不迎合人类**的多 agent 法庭。

- **消费群体当陪审团**：独立子 agent，动态匹配，权重最大（占 60%）
- **专家证人席**：产品/工程/备案/竞品/增长 5 位，主上下文扮演（占 40%）
- **两轮聚焦辩论**：第 1 轮独立举证 → 第 2 轮分歧质询
- **加权裁决**：三档结论（痛点 / 痒点 / 自嗨）+ 建设性意见

**硬约束**：省 token。总预算 8000（不含用户输入），超预算按降级规则处理。

## 1. 总体架构与文件结构

### 1.1 核心设计

消费群体从"常驻"改为"**产品驱动动态匹配**"——不预设固定群体，而是根据产品画像从候选库匹配 2-3 个最相关群体。这样：

- 不相关群体的画像和案例库完全不进上下文（省 token）
- 动态加权只在"被选中群体"之间分，不被无关群体稀释
- 宝妈做母婴类才被选中，学生做教育类才被选中，以此类推

### 1.3 文件职责切分

- `agents/` 放角色卡：主上下文扮演的角色卡直接 inline 进 prompt，消费群体画像常驻但精简
- `case-library/` 与画像分离：画像必须读（省不了），案例库只在子 agent 觉得"画像不够支撑判断"时按需读（省 token 关键）
- `scoring-rubric.md` 和 `debate-protocol.md` 把规则从主流程抽出来，SKILL.md 保持精简
- 新增群体只需往候选库丢一个 md + 一个案例库文件，匹配规则自动生效，不用改主流程

## 2. 多 Agent 角色定义与辩论协议

### 2.1 Agent 阵容

**A 类：主上下文扮演的专家证人**（5 位，不派子 agent，省 token）

| Agent | 核心职责 | 关注维度 | 默认姿态 |
|---|---|---|---|
| 产品经理 | 从产品价值主张、市场定位、差异化判断 | 需求真伪、市场大小、护城河、PMF 信号 | 中立举证 |
| 代码工程师 | 从技术可行性、维护成本、扩展性判断 | 技术栈合理性、复杂度、债务风险 | 中立举证 |
| 备案中介 | 从合规、资质、数据安全判断 | ICP/EDI/医疗/教育/金融备案、数据合规 | 中立举证 |
| 竞品分析师 | 从竞品格局、替代方案判断 | 竞品数量、替代方案、差异化空间 | 中立举证 |
| 增长黑客 | 从获客、留存、裂变判断 | CAC/LTV、留存曲线、裂变路径 | 中立举证 |

5 位在主上下文里依次发言，每个限定 ≤400 token，发言后不互相互动。

**B 类：独立子 agent 的消费群体陪审团**（2-3 个，动态匹配，权重最大）

每个被匹配到的消费群体派一个独立子 agent：

- **输入隔离**：子 agent 只拿到 ① 核心画像 ② 产品画像 ③ 辩论问题，**看不到其他 agent 的发言**（保证独立）
- **行为模拟**：按该群体真实行为模式回应——会不会下载、会不会用、会不会付费、会不会卸载、会不会推荐
- **按需读案例库**：子 agent 觉得画像不足以判断时，自己决定读不读 `case-library/xxx-cases.md`
- **输出结构固定**：返回 5 字段（见 2.4）

### 2.2 两轮聚焦辩论协议

```
第0步  产品画像解析（主上下文, ≤800 token）
       输入 → 提取：领域/场景/付费来源/技术形态
       输出：产品画像 + 匹配2-3个消费群体（含相关度+匹配理由）

第1轮  独立举证（互不可见）
  ├─ 1a. 消费群体子agent并行派发（Task工具，2-3个并发, 每个≤1200 token）
  │     返回5字段: USE_INTENT/PAY_INTENT/PAIN_MATCH/KEY_ARG/NEEDS_CASES
  └─ 1b. 主上下文5位专家证人依次发言（每个≤400 token, 共≤2000）
        产品→工程→备案→竞品→增长

第2轮  分歧聚焦质询（只派涉分歧群体）
  ├─ 主AI扫描第1轮发言, 识别≤3个关键分歧点
  │  （分歧点判定：≥2方立场矛盾，且该矛盾会导致三档裁决结论不同——即若不解决此分歧，裁决可能在痛点/痒点/自嗨之间摇摆）
  ├─ 对每个分歧点:
  │     - 主上下文专家补证（≤150 token/分歧点）
  │     - 涉分歧的消费群体子agent重派补证（≤500 token/个, 只给分歧点+该群体第1轮立场）
  └─ 输出: 分歧点 + 双方补证

第3步  加权裁决（主上下文, ≤1200 token）
       打分 + 动态加权 + 裁决 + 建设性意见
```

**为什么第 2 轮重派子 agent**：第 1 轮子 agent 只给立场，第 2 轮让涉分歧群体在"知道分歧点"的情况下补证，判断更扎实。为控预算，只派涉分歧的群体（通常 1-2 个），不重派全部。

### 2.3 Token 预算（硬约束，8000）

| 环节 | 预算 |
|---|---|
| 产品画像解析 | 800 |
| 第1轮 消费群体子 agent | 3 × 1200 = 3600 |
| 第1轮 专家证人 | 5 × 400 = 2000 |
| 第2轮 涉分歧群体补证 | 2 × 500 = 1000 |
| 第2轮 专家补证 | 3 × 150 = 450 |
| 最终裁决 | 1200 |
| **最坏总计** | **≈9050** |

**降级规则**（累计实际 token ≥ 7500 时按顺序执行）：
1. 第2轮专家补证跳过（只保留子 agent 补证）→ 省 450
2. 案例库读取关闭（子 agent 靠画像判断）→ 省可变量
3. 第2轮只处理最关键 1 个分歧点（其余分歧点直接进裁决）→ 省 500+

降级优先保：消费群体子 agent（第1轮）+ 最终裁决。

### 2.4 子 agent 固定输出字段

```
GROUP: <群体名>
USE_INTENT: <1-10> - <一句理由>
PAY_INTENT: <1-10> - <一句理由>
PAIN_MATCH: <痛点/痒点/自嗨> - <一句理由>
KEY_ARG: <≤50字>
NEEDS_CASES: <yes/no>
```

`NEEDS_CASES: yes` 时主流程才让子 agent 二次读案例库（按需触发，省 token）。

## 3. 评分维度、动态权重与裁决报告

### 3.1 三档裁决

| 档位 | 定义 | 触发条件 |
|---|---|---|
| **痛点** | 解决真实刚需，用户愿意付费/持续使用，市场可跑通 | 加权总分 ≥ 7.0 且消费群体 PAY_INTENT 均值 ≥ 6 |
| **痒点** | 有趣但不刚需，用户会用但不付费/不留存 | 加权总分 4.0–6.9，或 PAY_INTENT 均值 3–5 |
| **自嗨** | 创作者自我感动，目标群体根本不买账 | 加权总分 < 4.0，或消费群体 PAY_INTENT 均值 < 3 |

### 3.2 5 个评分维度（0-10 分）

| 维度 | 含义 | 主要打分方 |
|---|---|---|
| 需求真伪度 | 需求真实存在吗，还是臆想 | 消费群体为主 |
| 付费/留存意愿 | 用户会不会掏钱/持续用 | 消费群体为主 |
| 技术可行性 | 能不能稳定做出来 | 代码工程师为主 |
| 市场可跑通 | 获客成本、留存、裂变能否支撑 | 增长黑客 + 竞品分析师 |
| 合规风险 | 会不会被监管拍死 | 备案中介为主 |

**加权方式**：每个维度由"主要打分方"权重 60% + 其他 agent 平均分 40% 合成。

### 3.3 动态权重规则

消费群体总权重占整体 **60%**，5 位专家证人共占 **40%**（各 8%）。

消费群体**内部**按"与产品相关度"动态分配：

```
消费群体i的权重 = (相关度i / Σ相关度) × 60%

相关度判定（第0步产品画像解析时同步给出）：
- 高相关（3分）：产品直接服务该群体核心场景
- 中相关（2分）：产品部分功能触及该群体
- 低相关（1分）：群体偶发使用，非核心
- 不相关（0分）：不匹配，不派子agent
```

**例子**：一个母婴社区工具
- 宝妈 相关度 3，中小企业创业者 相关度 1（用于"宝妈创业卖货"场景）
- 宝妈权重 = 3/(3+1) × 60% = 45%，创业者权重 = 1/(3+1) × 60% = 15%
- 专家证人共 40%（5 位各 8%）

**边界情况**：
- 只匹配 1 个群体：该群体占 60%，专家占 40%
- 只匹配 0 个群体：降级为纯专家证人评判（消费群体权重 0），报告标注"未找到明确目标群体，裁决可信度降低"

### 3.4 裁决报告格式

**默认输出**（紧凑版，≤1200 token）：

```markdown
# Vibe 需求裁决报告

## 一句话裁决
【痛点 / 痒点 / 自嗨】— <一句话理由>

## 输入阶段识别
【想法点子 / PRD说明 / 成品URL】

## 产品画像摘要
- 领域: <...>
- 核心场景: <...>
- 付费来源: <...>
- 技术形态: <...>

## 评分总览
| 维度 | 得分 | 主要打分方 |
|---|---|---|
| 需求真伪度 | x.x/10 | 消费群体 |
| 付费/留存意愿 | x.x/10 | 消费群体 |
| 技术可行性 | x.x/10 | 代码工程师 |
| 市场可跑通 | x.x/10 | 增长+竞品 |
| 合规风险 | x.x/10 | 备案中介 |
| **加权总分** | **x.x/10** | |

## 消费群体陪审团（动态加权）
| 群体 | 相关度 | 权重 | USE | PAY | PAIN_MATCH | 匹配理由 |
|---|---|---|---|---|---|---|

## 关键论点（每方≤2条）
- 👩 宝妈: <KEY_ARG>
- 🧑‍💻 产品经理: <关键论点>
- 🛠️ 代码工程师: <关键论点>
- 📋 备案中介: <关键论点>
- 🥊 竞品分析师: <关键论点>
- 📈 增长黑客: <关键论点>

## 分歧点（第2轮质询结果）
1. <分歧点> — 双方补证各一句

## 置信度
【高 / 中 / 低】— <理由>

## 关键风险点
1. <风险> — <来源agent>
2. <风险> — <来源agent>

## 建设性意见
- <2-3条可执行改进方向，或"建议放弃"理由>
```

**完整辩论实录**（用户要求时才输出，不计入 1200 预算）：
- 在紧凑版基础上追加"## 完整辩论实录"章节
- 按第1轮 → 第2轮顺序，逐个 agent 完整发言
- 单独保存到 `verdict-full.md`，避免主报告臃肿

### 3.5 建设性意见生成规则

- **必须基于辩论中的具体论点**（引用某 agent 的 KEY_ARG）
- **痛点档**：给"如何放大优势"建议（增长黑客视角）
- **痒点档**：给"如何转痒点为痛点"建议（产品+增长视角）
- **自嗨档**：给"是否值得继续"判断 + "如果硬要做需要哪些前提条件"
- **禁止空话**：不能出现"加强运营""优化体验"这类无指向建议

## 4. SKILL.md 主流程、输入解析与匹配规则

### 4.1 触发条件

```yaml
---
name: vibe-need-judge
description: >
  判断一个 vibe coding 应用到底解决了真痛点、只是痒点、还是创作者自嗨。
  通过多 agent 法庭辩论：消费群体当陪审团（独立子agent，动态匹配，权重最大），
  产品/工程/备案/竞品/增长5位专家当证人（主上下文扮演），两轮聚焦辩论后加权裁决。
  不迎合人类，纯粹理性客观。支持想法/PRD/成品URL灵活输入。
---
```

**触发短语**：
- "判断这个 vibe coding 应用/项目"
- "这个应用是自嗨还是痛点"
- "这个项目解决需求了吗"
- "评价一下这个 vibe coding"
- "这个想法值不值得做"

### 4.2 主流程

```markdown
## 主流程

### 第0步：输入解析与产品画像（≤800 token）

1. 识别输入类型：
   - 一句话/几句话 → 想法阶段
   - 结构化说明（功能/用户/场景） → PRD阶段
   - URL/Demo链接 → 成品阶段（如有URL，先用WebFetch抓取页面内容）

2. 提取产品画像（固定4字段）：
   - 领域（母婴/教育/SaaS/...）
   - 核心场景（用户在什么情境下用）
   - 付费来源（谁付钱、为什么付）
   - 技术形态（App/Web/小程序/工具/平台）

3. 读取 references/agents/consumer-groups/_matching-rubric.md
   对候选库每个群体打相关度（0/1/2/3），选 2-3 个相关度≥2 的群体
   （不足2个时降级，见第2节边界情况）

4. 输出：产品画像 + 匹配群体列表（含相关度+匹配理由）

### 第1轮：独立举证

1a. 消费群体子agent并行派发（Task工具，2-3个并发）
    - 每个子agent输入：
      · references/agents/consumer-groups/_subagent-template.md（prompt模板）
      · 该群体核心画像 references/agents/consumer-groups/<group>.md
      · 产品画像
      · 输出格式要求（5字段）
    - 子agent自行决定是否读 case-library/<group>-cases.md（NEEDS_CASES=yes时）
    - 返回5字段

1b. 主上下文依次扮演5位专家证人发言（读对应角色卡）
    - 每位≤400 token
    - 顺序：产品经理 → 代码工程师 → 备案中介 → 竞品分析师 → 增长黑客

### 第2轮：分歧聚焦质询

1. 主AI扫描第1轮所有发言，识别≤3个关键分歧点
   （分歧点判定：≥2方立场矛盾且影响裁决结论）
2. 对每个分歧点：
   - 主上下文专家补证（≤150 token）
   - 涉分歧的消费群体子agent重派补证（≤500 token，只给分歧点+该群体第1轮立场）
3. 检查token预算，若接近8000则按降级规则处理

### 第3步：加权裁决

1. 读取 references/scoring-rubric.md
2. 每个维度按"主要打分方60% + 其他agent平均40%"合成得分
3. 消费群体内部按相关度动态分配权重（占整体60%）
4. 专家证人各占8%（共40%）
5. 计算加权总分 → 三档裁决（痛点≥7.0 / 痒点4.0-6.9 / 自嗨<4.0）
6. 生成建设性意见（按档位规则，引用具体论点）
7. 填充 templates/verdict-report.md 模板，输出紧凑版报告

### 可选：完整辩论实录
用户要求时，追加"## 完整辩论实录"章节或单独保存 verdict-full.md
```

### 4.3 群体匹配规则（_matching-rubric.md）

每个消费群体在画像文件顶部带**匹配标签**，主流程用标签做匹配：

```markdown
# 宝妈·核心画像

## 匹配标签
- 适用领域: 母婴, 育儿, 家庭, 亲子, 健康, 教育(低龄), 电商(家庭消费)
- 适用场景: 育儿管理, 家庭采购, 孩子教育, 健康管理, 社区分享
- 不适用: B端工具, 开发者工具, 汽车后市场, 金融专业工具
```

**匹配算法**：

```
对每个候选群体:
  if 产品领域 ∈ 群体.适用领域 AND 产品场景 ∈ 群体.适用场景:
      相关度 = 3 (高)
  elif 产品领域 ∈ 群体.适用领域 OR 产品场景 ∈ 群体.适用场景:
      相关度 = 2 (中)
  elif 群体与产品有间接关联(由主AI判断):
      相关度 = 1 (低)
  else:
      相关度 = 0 (不匹配,不派)

选 top 2-3 个相关度≥2的群体
```

### 5.2 消费群体核心画像结构（7 个文件统一格式）

以 `baoma.md` 为例：

```markdown
# 宝妈·核心画像

## 匹配标签
- 适用领域: 母婴, 育儿, 家庭, 亲子, 健康, 教育(低龄), 电商(家庭消费)
- 适用场景: 育儿管理, 家庭采购, 孩子教育, 健康管理, 社区分享
- 不适用: B端工具, 开发者工具, 汽车后市场, 金融专业工具

## 人群基础特征
- 年龄: 25-40岁女性
- 时间: 碎片化，孩子睡后才有整块时间
- 设备: 手机为主，熟悉微信/小红书/抖音
- 付费: 愿为"省心""孩子好"付费，价格敏感度中低
- 决策: 群体影响大（妈妈群/小红书口碑）

## 真实痛点（常被忽略的）
- 育儿焦虑，怕做错
- 时间被切得很碎
- 怕孩子落后，又怕鸡娃过头
- 家庭消费决策压力大

## 真实行为模式（辩论时模拟）
- 下载前必看小红书/妈妈群评价
- 付费前会问"有没有平替"
- 复杂操作直接放弃，不会研究
- 用了3天没效果就卸载
- 真心觉得好会强烈推荐给其他妈妈

## 你不会做的事（避免迎合）
- 不会因为"功能多"就给好评
- 不会因为"AI加持"就感兴趣
- 不会为了"创新"买单，只为"省心/孩子好"买单

## 案例库触发线索（何时需要读 case-library/baoma-cases.md）
- 产品涉及育儿/教育/健康但场景模糊时
- 不确定该群体会不会真用时
```

**7 个群体差异化要点**：

| 群体 | 关键特征 | 付费触发 | 卸载触发 | 典型自嗨陷阱 |
|---|---|---|---|---|
| 宝妈 | 碎片时间、育儿焦虑、群体影响 | 省心/孩子好 | 3天没效果 | 以为宝妈"什么都买" |
| 学生 | 预算紧、跟风、用爱发电 | 便宜/刚需/社交 | 要付费/太复杂 | 以为学生"爱尝鲜就会用" |
| 中小企业创业者 | 资源紧、要ROI、决策快 | 省钱/赚钱/提效 | 看不到效果 | 以为创业者"什么都愿意试" |
| 中老年人 | 信任门槛高、操作敏感、家庭决策 | 健康/便民/子女推荐 | 字小/操作复杂 | 以为中老年"市场大就行" |
| 职场白领 | 时间紧、追求效率、AI工具尝鲜 | 真省时/可报销/能晒 | 要手动配置/学习成本高 | 以为白领"爱AI就会用" |
| 自由职业者/独立开发者 | 技术懂、预算敏感、爱DIY | 真赚钱/省重复劳动/无开源平替 | 闭源收费/有平替/自己能写 | "创作者=用户"的错觉 |
| 内容创作者 | 数据焦虑、多平台运营、跟风口 | 涨粉/变现/省剪辑时间 | 效果不可量化/学习成本 | 以为创作者"什么工具都买" |

## 三档裁决（最终结论）

- 痒点: 加权总分 4.0-6.9，或 PAY_INTENT 均值 3-5

|---|---|---|

## 6. 边界情况、错误处理与测试验证

### 6.1 边界情况与处理

| 边界情况 | 处理方式 |
|---|---|
| 匹配到 0 个消费群体 | 降级为纯专家证人评判（消费群体权重 0），报告标注"未找到明确目标群体，裁决可信度降低" |
| 匹配到 1 个消费群体 | 该群体占 60%，专家占 40%，正常运行 |
| 输入是 URL 但抓取失败 | 提示用户"无法访问，请提供产品文字描述"，回退为想法阶段处理 |
| 输入极度模糊（如"做个AI应用"） | 第0步直接返回"产品画像解析失败，请补充：领域/场景/付费来源"，不进入辩论 |
| 某消费群体子 agent 超时/失败 | 跳过该群体，剩余群体重新分配权重，报告标注"某群体陪审缺席" |
| 第2轮分歧点识别为 0 | 跳过第2轮，直接进裁决，报告标注"首轮无关键分歧" |
| token 累计实际 ≥ 7500 | 按降级规则：专家补证跳过 → 案例库关闭 → 第2轮只处理 1 个分歧点 |
| 用户要求完整辩论但 token 已超 | 完整辩论保存为单独文件，主报告仍紧凑，提示"完整实录见 verdict-full.md" |

### 6.2 输入阶段可信度标注

| 输入阶段 | 可信度 | 说明 |
|---|---|---|
| 想法点子 | 低 | 只有概念，技术/市场/合规都没验证 |
| PRD 说明 | 中 | 有结构化设计，但未经验证 |
| 成品 URL | 高 | 可观察实际产品，消费群体可"真实体验"后判断 |

成品 URL 时，消费群体子 agent 会先被提示"基于该 URL 的产品形态判断"（如有 WebFetch 抓取的页面内容），判断更接近真实。

### 6.3 测试验证策略

skill 上线前用 **3 个代表性测试用例**验证：

| 测试用例 | 输入 | 预期裁决 | 验证点 |
|---|---|---|---|
| 明显自嗨 | "做个 AI 给程序员写诗鼓励他们" | 自嗨 | 消费群体（程序员/自由职业者）PAY_INTENT 低，能识别"创作者自我感动" |
| 典型痒点 | "做个 AI 帮人取网名" | 痒点 | 有用但不付费，留存差，增长黑客能指出跑不通 |
| 真痛点 | "做个中小商家用的简易进销存小程序" | 痛点 | 中小企业创业者 PAY_INTENT 高，代码工程师确认可行，备案中介指出门槛 |

每个测试用例验证：
- 群体匹配是否准确
- 子 agent 是否独立发言（不互相影响）
- 评分加权是否正确
- 报告字段是否完整
- token 是否在预算内

### 6.4 已知局限（写进 SKILL.md 末尾）

- **消费群体仍是被模拟的**：子 agent 按画像模拟，不等于真实用户调研，裁决是"理性推断"而非"市场验证"
- **专家证人在主上下文扮演**：不是真正独立 AI，可能有立场泄漏，但通过消费群体子 agent 独立性对冲
- **无真实数据支撑**：不抓竞品数据、不查真实留存，全靠 agent 推理，适合早期筛选不适合最终决策
- **中文产品语境**：备案中介角色针对国内合规，海外产品需调整
